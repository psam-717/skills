# Hermes Upstream PR

Ship a bug fix developed against the managed install (`$HERMES_HOME/hermes-agent`) to the upstream repo as a PR — patch in place, prove in an isolated clone, push from a fork. Use whenever the fix touches the hermes-agent repo and the user wants it upstreamed (or a local patch that must survive cleanly).

## Always-on rules

- **Read CONTRIBUTING.md + `.github/PULL_REQUEST_TEMPLATE.md` in the repo first** and follow them literally: branch `fix/<desc>`, conventional commit (`fix(desktop): ...`), template sections filled, checklist honest.
- **Prove new invariant tests red on base** — apply the test diff to a clean `origin/main` clone WITHOUT the source fix, run, show failure; then apply the source diff and show green. State both in the PR body.
- **Never branch or stash in the live checkout** — the install guard blocks `git stash`/`git checkout` there (mixing module versions in the running runtime). Edit files freely; do git surgery in the scratch clone.
- **Scope commits by path** (`git add apps/desktop`), never `git add -A` — the live checkout carries unrelated dirty files (local patches) that must not ride along in the PR.
- **Native binaries take native paths.** `gh`, `git`, `python` and `node` reject `/c/...` as arguments: git reports the repo "does not exist", python resolves `C:\c\Users\...`. Pass `C:/...`. Repeat offenders: `gh --body-file`, `git commit -F`, `git clone <path>`, `python -c "...open(r'$VAR/...')"`. Do the `cd` in bash (a builtin accepts MSYS paths), then hand the tool native paths.
- **Run the duplicate check BEFORE building anything.** `gh search prs` + `gh search issues` (open and closed) for the feature; a request that already has several open PRs changes the deliverable — consolidate onto the closest/smallest one, review it, or ship deliberately smaller and disclose the overlap in the body. Bring the evidence to the user and let them choose.
- **Confirm the PR EXISTS before you "update" it.** A session that died between `git push` and `gh pr create` leaves a pushed branch and NO PR, and the user's "the PR we opened" is not evidence. Check the two facts separately: `gh api repos/<user>/<repo>/git/ref/heads/<branch>` (branch pushed?) and `gh pr list --repo <org>/<repo> --head <user>:<branch> --state all` (PR open? `[]` means it was never created) — cross-check with `gh pr list --repo <org>/<repo> --author <user> --state all`. Then say plainly which one is missing and open it fresh; do not hunt for a PR that does not exist.
- **A user report of "a failing CI check on the PR" is a hypothesis — locate the failure before touching anything.** Triage in this order: `gh pr checks <n>` ("no checks reported" plus upstream runs at `action_required` = the PR's CI never started), then `gh run list --repo <user>/<repo> --limit 30` for the FORK's own push runs, then the notification feed that generated the email (`reason == "ci_activity"`). A fork's `main` push workflows fail on their own schedule and are not the PR's checks — see `references/fork-ci-noise.md`. Never let the user's attribution of an email to a specific PR steer the fix; state plainly which artifact actually failed.

## Procedure

0. **Diagnose on live state first** (desktop-app bugs):
   - The PACKAGED app accepts Chromium's own flag — relaunch it with
     `Start-Process '…\release\win-unpacked\Hermes.exe' -ArgumentList
     '--remote-debugging-port=9222'` (only when the restart is yours to make;
     tell the user) to get a CDP port; relaunch without the flag when done.
   - Reproduce signal-driven reconnect/re-render bugs without a human at the
     window: fire synthetic event storms from `Runtime.evaluate` —
     `window.dispatchEvent(new Event('online'))`, `focus`, and
     `document.dispatchEvent(new Event('visibilitychange'))` in a loop.
   - Churn metrics that prove the bug and the fix: `grep -c "ws closed"
     <profile>/logs/gui.log` per profile (the sick profile has orders of
     magnitude more), and `session.reclaimed|ws_orphan_reap` counts in
     `%LOCALAPPDATA%\hermes\logs\desktop.log`. Report before/after numbers.
   - A backgrounded Electron window throttles renderer timers hard — a
     starved in-page sampler means "not focused", not "idle".
1. **Develop against the live checkout** (edits are fine): patch, `npm run typecheck` (in `apps/desktop` for TS), targeted `npx vitest run <files>`, then the full `npm run test:ui`.
2. **Format before committing**: `npx eslint --fix <changed.ts>` + `npx prettier --check <changed files>` — warnings block a clean PR.
3. **Split the diff**: `git diff -- <source files> > src.patch` and `git diff -- <test files> > tests.patch` (both scoped to the changed subdirectory, excluding unrelated dirty files).
4. **Scratch clone** (shared, real disk — the profile scratch dir, never /tmp):
   ```bash
   git clone --shared "$HERMES_HOME/hermes-agent" <scratch>/clone
   cd <scratch>/clone && git fetch https://github.com/NousResearch/hermes-agent.git main --quiet
   git branch fix/<desc> FETCH_HEAD && git checkout fix/<desc>
   ```
   Do the `git checkout` in a SEPARATE terminal call from any command mentioning the live checkout path — the guard pattern-matches the command line, not the cwd.
5. **Junction node_modules** (no npm install needed) with PowerShell, at BOTH levels:
   ```powershell
   New-Item -ItemType Junction -Path <clone>\node_modules -Target <live>\node_modules
   New-Item -ItemType Junction -Path <clone>\apps\desktop\node_modules -Target <live>\apps\desktop\node_modules
   ```
6. **Red-on-base proof**: `git apply tests.patch` → run the new tests → they must FAIL. Then `git apply src.patch` → run the full targeted suite → green.
7. **Commit** with conventional message + `Fixes #<issue>` in the body, push to a fork (`gh repo fork NousResearch/hermes-agent --clone=false`, `git remote add fork`, push branch).
8. **Open the PR** with `gh pr create --repo NousResearch/hermes-agent --base main --head <user>:<branch> --body-file`. Account has READ on upstream — fork flow is mandatory.
9. **Verify the PR** with `gh pr view` (state, additions/deletions, file list) before reporting the URL.
10. **Review follow-ups**: automated AI reviewers comment on PRs and cite real line-level gaps — read them, address each point with a follow-up commit plus a reply comment explaining the reasoning (including deliberate simplifications). The clone branch already carries the first commit, so COPY the patched files from the live tree into the clone instead of re-applying cumulative patches, and prove the new test red on the PREVIOUS commit before the fix (`git diff -- <src> > fix.patch && git checkout -- <src>` → run new test → RED → `git apply fix.patch` → GREEN).
11. **Rebase round** (when a reviewer says "current main added X after this branch's base" or asks you to rebase):
    - Check what actually changed on main for YOUR files before deciding effort — fetch the file blobs from main via the GitHub API (`contents?ref=main` → base64) and diff against the branch base in Python; the compare API's files list caps at 300 entries on a fast-moving repo and ABSENCE THERE IS NOT EVIDENCE a file is unchanged.
    - Fetching current main into the `--shared` clone can exceed the 180s terminal default — run it in background (`git fetch <upstream> main:upstream-main`) and verify the ref exists before using it.
    - `git checkout -b fix/<desc>-v2 upstream-main && git cherry-pick <sha1> <sha2> …` — resolve the small conflicts, run the targeted suite, then implement the reviewer's ask.
    - When main now HAS the policy/module the reviewer wants mirrored (e.g. a shared liveness/decision module), REUSE it verbatim — import the module, don't re-implement the logic — so a later rebase is trivial and the semantics match upstream by construction.
    - Force-push the v2 branch to the SAME head branch name (`git push fork v2:fix/<desc> --force`) — the PR and its review threads survive; old threads mark outdated, which is expected. Update the PR body (`gh pr edit --body-file`) and reply on each review thread (`gh api repos/<org>/<repo>/pulls/<n>/comments/<id>/replies -f body=…`).
12. **Local build**: for desktop changes, `npm run pack` in `apps/desktop` after killing Hermes.exe (packager keeps a rollback at `release/win-unpacked.bak`). Relaunch and verify live.
13. **After the merge** (maintainers cherry-pick external PRs with authorship intact and close the original in favour of the merged one — verify, don't assume):
    - Confirm your commits on `main` are attributed to the user: `gh api repos/<org>/<repo>/commits/<sha> --jq '{author: .author.login, name: .commit.author.name}'`.
    - The GitHub Contributors graph/cache lags up to ~24h after a merge — absence there is not evidence of lost attribution. Point the user at `…/commits?author=<user>` (works immediately) and their profile's activity feed, and tell them the graph catches up.
14. **Teardown once merged** — safe-delete the scratch clone, junctions FIRST:
    - Delete the two node_modules junctions with PowerShell `[IO.Directory]::Delete('<path>')` (removes only the reparse point) BEFORE any recursive delete — MSYS `rm -rf` FOLLOWS junctions and would wipe the live install's `node_modules`. `cmd //c rmdir` from git-bash silently fails on them.
    - `rm -rf <scratch>` from the profile scratch dir hits `Device or resource busy` while a shell's cwd sits inside the tree — `cd $HOME` first; if an EMPTY dir still won't die, `powershell Remove-Item -Recurse -Force` it. Verify the live install's `node_modules` still lists afterward.
    - Delete the fork's merged head branch: `gh api -X DELETE repos/<user>/<repo>/git/refs/heads/<branch>` (merged commits are safe on upstream). **A 404 or 422 `Reference does not exist` means it is already gone — GitHub/maintainer tooling deletes the head branch on merge (even for fork PRs), so treat that as success, not as a failed cleanup.** Verify with `gh api repos/<user>/<repo>/git/ref/<heads/branch>` before assuming you have anything to delete.
    - The observed merge flow: the maintainer force-pushes a rebase of your branch onto current `main` (`head_ref_force_pushed`), sets `auto_rebase_enabled`, then merges — the resulting commit keeps your authorship (`author.login` = your account, `committer` = the maintainer) with your commit message. Verify with `gh api repos/<o>/<r>/commits/<sha> --jq '{author:.author.login, name:.commit.author.name, committer:.commit.committer.name}'` and confirm ancestry with the compare API (`behind_by: 0`), not the "Merged" badge.

## CI parity (run the units CI runs, then base-compare)

- CI for a JS/TS PR is `.github/scripts/run-workspace-checks.mjs`: it runs **every** `check:*` script the changed package declares. For `apps/desktop` that is four units — `check:lint` (`typecheck && eslint src/ electron/`), `check:test:ui`, `check:test:desktop:platforms` (`vitest run --project electron`), `check:test:desktop:all` (packages the app). Run them yourself before opening the PR; `node .github/scripts/run-workspace-checks.mjs --list` prints the set. A reusable one-lane-at-a-time runner, a watcher that cannot go quiet, and the measured lane budget: `references/parity-runs.md`.
- **Local lanes gate the BODY, not the PR.** GitHub runs these same units the moment the PR exists, so running them locally is never a prerequisite for opening — it is what lets the verification section quote measured numbers and keeps a known-red lane from greeting a maintainer. If a lane cannot be completed on this host, open anyway and fill that row from CI's result, saying which rows came from CI. Spell that split out for the user in plain language BEFORE the long run starts — which lanes are cheap and local, which one is CI-authoritative and why, and what waiting actually buys — and offer "measured locally" against "open now, fill from CI" as a decision with your recommendation. This user asks exactly that question, and a short table answers it where a status dump does not. (One lane that is known-red before opening is worth the wait: it is a defect in your own change, and the base comparison is what identifies it.)
- Restore the junctioned `apps/desktop/node_modules` from the managed install and some lanes fail for reasons that are **not yours**: the tree predates the deps upstream `main` added (`dbus-native`, `@novnc/novnc`, `@types/proxy-from-env` — the last three surface through the repo's own `assert-root-install` preflight, which tells you to run `npm ci`). Phantom `typecheck` errors of the same kind appear in the clone but not in the managed checkout. Only `npm ci` in a standalone clone fixes it; base-compare and name the cause instead.
- **Base-compare every noisy lane** by switching the clone to a detached `FETCH_HEAD` (no patches) and re-running it: `test:ui` and the electron project both carry host-specific failures on Windows (no ssh ControlMaster/mux, no `zsh`, no display, no `dbus-native`). Identical counts on base is the claim to make, with both numbers quoted.
- **A new i18n key needs its generated catalog committed.** `apps/desktop/locales/_keys.desktop.json` is a committed artifact emitted from `src/i18n/en.ts`; adding a key without running `npm run i18n:keys` in `apps/desktop` and committing the result fails `scripts/i18n-keys.test.mjs` in the electron lane ("… is out of date with src/i18n/en.ts"). In a base comparison this shows up as the ONE extra failing file that looks like your change breaking something — regenerate, commit, re-run, and the delta disappears. Never explain it away in the body instead.
- Two mandatory PR checks are easy to miss: **Contributor Attribution** (a new commit author email must be mapped — an `NNN+user@users.noreply.github.com` id+login noreply is auto-skipped, anything else needs `contributors/emails/<email>`) and **History Check** (the branch must share an ancestor with `main`, so never push an orphan/re-init history).
- CONTRIBUTING.md's "run `scripts/run_tests.sh`" is the *Python* suite; for a desktop-only diff the correct statement is that no Python file is touched and CI's change classifier does not run that suite — say it plainly and untick the template's pytest box rather than ticking it with a footnote.
- **`python scripts/check` is NOT "N/A because the diff is TypeScript".** Its own `--help` says what it covers — the workflow guards, ruff, and the **code-health ratchet** — and CONTRIBUTING states the ratchet judges TS units too (`scripts/code_health/ts_units.mjs`: file ≤ 2,000 lines, function ≤ 300 lines, complexity ≤ 20, with new violations blocking even where existing ones are grandfathered). CI runs it from `.github/workflows/lint.yml`, so a new `.tsx`/`.ts` file in the PR is in scope. Run it in the clone (`python scripts/check`, comparing against the merge-base with `origin/main`) and tick or untick on the measured result; only the pytest box is genuinely N/A for a desktop-only diff.
- **The ratchet blocks GROWTH of any already-over-target file — settle that BEFORE fixing the file list.** `ENFORCEMENT = "blocking"` (read from the base revision) and a unit already over target "keeps its own current value as its cap … it may only go down", so adding ONE line to a 5,000-line i18n catalog or to an already-oversized component is a red check on an otherwise-clean diff — and a new user-facing string is felt everywhere, because it lands in every catalog plus the type module. Its CI wiring is `.github/workflows/lint.yml` (`python scripts/check --only health --base HEAD^1`) and it takes seconds, so run it as soon as the diff is stable, well before the parity lanes. Remedies, in the order the repo itself lists them: (a) **offset** the growth in the same PR the way upstream's own "CI on the branch" commits do — those are pure removals of retired strings and dead code — while the ratchet's fix text says to move an existing function/class into a topical sibling (`<stem>_<topic>`); (b) **waive on the line** — `// health: allow FILE_LINES -- <why>` is parsed from comment trivia in TS as well as `#`-style in Python, precedent exists on over-target files, and reviewers read the reason: the honest route when the real remedy is a refactor outside this PR's scope; (c) **remove the growth**: a new string that duplicates an EXISTING label can reuse that key instead of adding one, which deletes the entire catalog delta and its findings; (d) split the over-target catalogs into topic siblings (the letter of the remedy, a large diff). Each option changes the shape of the PR, so lay them out with counts and let the user choose — do not silently waive eight files, and never open with a lint job known to be red.

## Pitfalls
- **The code-health ratchet fails ANY growth of an over-target file, and it runs on every PR** — `.github/workflows/lint.yml` → `python scripts/check --only health --base HEAD^1` with `ENFORCEMENT="blocking"`. One added line to a 5,000-line i18n catalog, or one line inside a function already at its cap (cap = its value on the base revision, "it may only go down"), turns the lane red. Run `python scripts/check` BEFORE opening the PR. The remedy is the one it prints: move the topic into a sibling (`<locale>_composer.ts`, `types_composer.ts`, `ru_plural.ts`, a small extracted component) and keep the moved text verbatim — compare the moved block with `git show HEAD:<file>` whitespace-insensitively to prove it, since prettier re-wraps long values at the sibling's shallower indent. Type gotchas: only `en` is a strict `Translations`, the other locales are `defineLocale` overrides, so their composer sibling takes `TranslationOverrides['composer']`, not the full type. A NEW key also needs `npm run i18n:keys` re-run and committed (`locales/_keys.desktop.json`), or the electron lane's `scripts/i18n-keys.test.mjs` fails.
- **A lang that grows a catalog** also has to keep the sparse locales' shape: `ar_chat.ts` / `zh-hant_chat.ts` are topic-overlay files and may grow freely, the eight root catalogs may not.
- **A fork PR's CI is gated on a maintainer approving the run**: `gh run list --branch <branch>` shows the workflows created with conclusion `action_required` and `gh pr checks` prints "no checks reported" until someone clicks Approve. That is not a failure to fix — say so and stop polling.
- **Fork-only workflows fail and email while the PR is perfectly fine.** In this fork the observed pair is `auto-fix lint issues & formatting` (`pull request create failed: GraphQL: GitHub Actions is not permitted to create or approve pull requests (createPullRequest)` — a repo setting; the first job still succeeds and force-pushes the eslint patch to `bot/js-autofix`, which makes the log misleading) and `Canary Release` (`ChannelError: Channel repository authority mismatch` — a fork is not the release-authority repo, so it fails on its daily schedule forever). Rule: any upstream workflow that PUSHES or RELEASES cannot succeed in a fork, so report it as fork infrastructure, never as a defect. Silence it by disabling the workflow in the fork (`gh api repos/<user>/<repo>/actions/workflows` for ids → `gh api -X PUT …/workflows/<id>/disable`; `/enable` reverses it). Do NOT instead enable the repo's "Allow GitHub Actions to create and approve pull requests" setting — read the fork's actual knobs first (`gh api repos/<user>/<repo>/actions/permissions/workflow` → `can_approve_pull_request_reviews`; `gh api repos/<user>/<repo>` → `allow_auto_merge`; both false on psam-717/hermes-agent, `main` unprotected). With auto-merge off the bot merely opens a PR that sits in the fork forever; with auto-merge on the formatting commit lands on fork `main`, diverging it from upstream and breaking the `gh repo sync` the next PR branch depends on. Disabling a remote workflow is a state-changing repo write — surface the commands and consequence for approval. Taxonomy and commands: `references/fork-ci-noise.md`.
- **Jobs stuck `queued` in a fork will never start — `queued` is not `failed`.** Upstream's lanes request org-scoped larger runners (`ubuntu-latest-32-core` in `js-tests.yml`/`nix.yml`/`rust-tests.yml`, `windows-latest-32-core` in `tests-os.yml`), so in a personal fork no runner matches the label and those jobs sit `queued` indefinitely while the plain `ubuntu-latest` jobs in the same run complete. Read the label before reporting a hang: `gh api "repos/<user>/<repo>/contents/.github/workflows/<file>?ref=<sha>" --jq .content | base64 -d | grep -oE "runs-on: [^ ]+"`, then say which lane can never run here rather than waiting on it or calling it red.
- **Rebasing onto a main that moved thousands of commits: re-apply generated/derived files, never merge them.** When the conflicting files are catalogs, generated key lists or anything a script produces, take the base version wholesale (`git checkout <base> -- <paths>`), re-add the feature's content, then RE-RUN the generator/split against the new base. Merging the old split into new base files produces a half-state that compiles in your head and fails in CI.
- **A wholesale `git checkout <base> -- <paths>` silently drops lines your commit added to a DIFFERENT file of the same category.** Adding a catalog key means a value line in every locale AND a type declaration where the shape lives (`types.ts` → after a split, the type sibling). Take the base catalogs and the type is gone — the value keys then fail with `TS2353 ... does not exist in type`. Only the typecheck pass that contains the changed code catches it, so run that pass (`tsc -p .`), not just the fast one, after any resolution.
- **Prove a lane delta is a flake, do not assume it.** Compute failing FILE SETS, not counts: `grep -aoE '^ ❯ \|electron\| [^ ]+' <log> | sed 's/.*|electron| //' | sort -u` then `comm -23 patched base`. For each file in the delta, re-run it in isolation on the patched tree (`npx vitest run --project electron <file> <file>`); "both pass in isolation, 6/6" is the claim to write in the body. Windows flakes seen: a 30 s native-verification timeout under full-suite load, and `EPERM` on a vitest temp dir during a ConPTY probe.
- **Prove a typecheck error is base-identical by running that exact pass on the base commit** in the same clone (`git checkout --detach origin/main` → `npx tsc -p tsconfig.<project>.json --noEmit` → restore the branch). Junctioned `node_modules` predating a dependency main just added produces errors in files you never touched; quote "the same three lines on the unpatched tree" rather than pleading environment.
- **Check whether the PR already exists before "updating" it.** `gh pr list --repo <o>/<r> --head <user>:<branch> --state all` — a branch pushed to the fork is NOT a PR, and a session that died between `git push` and `gh pr create` leaves exactly that state.
- **Check every touched file for drift before porting.** Compare `git rev-parse HEAD:<path>` with `gh api repos/<o>/<r>/contents/<path>?ref=main --jq .sha`: identical files copy over wholesale, drifted ones get the edit re-applied in the clone (a patch cut against the managed checkout will not apply). A main that moved thousands of commits WILL have churned the hot files — 7 of 11 touched i18n catalogs had.
- **Port i18n keys as the FIRST property of the file's own `composer: {` block.** Anchoring after another key can split a multi-line string value; the completeness tests compare key SETS, not order. Some locales keep their strings in topic files (`<locale>_chat.ts`, `_chrome.ts`) that the root catalog recomposes — grep before assuming. Every catalog that path touches is already over the code-health file target, so the new key is also a ratchet decision (see the over-target bullet in CI parity) — and check whether an identical label already exists in another i18n group before minting a key at all.
- **`npm run typecheck` can die as a V8 abort with no diagnostics** (exit 134 partway through the first of its four `tsc` passes). That is memory, not types: re-run it alone with `NODE_OPTIONS=--max-old-space-size=8192`, and never beside a test suite.
- **`npm run pack` fails with `EBUSY … rmdir release\win-unpacked`** when it starts seconds after the app quits — Windows still holds handles and electron-builder treats that as fatal. Wait for `Hermes.exe` to disappear, then rename the tree aside yourself with retries (`win-unpacked.prev` is the rollback; restore it if the pack fails, and don't relaunch if the app already came back). Quitting the app also kills the agent session driving the build, so run wait → pack → relaunch as a detached script (`Start-Process -File …`), never from the session's own process tree.
- **Never let a subagent own a long CI run.** Its backgrounded suites die with the child (`Delegation owner exited before recording a terminal result`) and the numbers are void. Give children bounded work; run lanes from a detached parent-owned job and poll its log file. Launch it by handing the shell the SCRIPT PATH as one argument (`Start-Process bash.exe -ArgumentList @('/c/path/run-parity.sh') -WindowStyle Hidden`) — `-ArgumentList @('-lc','cmd with spaces')` gives the shell a mangled command and the job silently never starts.
- **A lane that DIED is not a lane that FAILED.** `Error: Worker exited unexpectedly` from vitest is the host running out of memory, not a test verdict — the same run on the base tree dies too, so the comparison you think you have is void (a crashed run also leaves no `Test Files / Tests` summary to quote). Re-run the lane single-threaded (`npx vitest run --project ui --no-file-parallelism`) with `NODE_OPTIONS=--max-old-space-size=8192`, identically on both trees, and name the deviation from CI's plain invocation in the body. **Single-threaded is not a rescue for a big lane — measure the file count before starting it.** `find apps/desktop/src -name '*.test.ts*' | wc -l` is ~1,239 for the `ui` project: serially that is one file every few minutes (2 files in 22 min; the worker logged ~115 s of CPU across 25 min of wall time), so the number never arrives. When the full lane cannot finish inside a sane budget, run the CHANGED test files directly on both trees plus the cheap lanes, and hand the full lane to CI — the body then says which lanes were measured locally with their base counts and which one is CI-authoritative *because this host cannot complete it*, naming the reason instead of ticking the box. Same for a lane whose last step is release-only tooling (`check:test:desktop:all` ends in `dist:win:msix`): base-compare it or name the missing toolchain — never tick the box.
- **Resuming a dead session's PR workspace: reuse the tree, never the numbers.** `<cache>/upstream-pr-<slug>/` holds `clone` (base), `clone-main` (branch), `parity*/` logs, `pr-body.md` and the commit message. Re-establish the facts that decide the next action before trusting any of it — `git log -1 --format=%B` (does the commit already carry the newest edit?), `git status` in each tree, `gh api .../compare/<base>...main --jq .behind_by` (is a rebase needed? 0 = no), and a per-file comparison of tree vs branch that IGNORES line endings (`diff --strip-trailing-cr`) before concluding a file drifted. A prepared body carrying a placeholder or counts from a crashed run is a draft, not a claim.
- **Comparing a branch tree against the managed checkout WILL show phantom drift.** The managed checkout is usually older than the branch's base, so files that upstream added after it (new i18n catalogs, new locale keys) look like differences in YOUR files. Diff `--strip-trailing-cr`, separate upstream drift from your edit, and port only your hunk — never copy the managed file over the branch's.
- **Answer "does the branch contain X?" from the COMMITTED tree, never the working copy.** The managed checkout, the branch tree and your scratch edits diverge by design (a fix can be committed at 23:47 while the live file was last written at 23:37 and an upstream base moved 2,000 commits under both). `git show HEAD:<path> | grep -n '<rule>'` on the branch tree is the only evidence that the PR carries the behaviour; quote the file and line numbers, and check the adjacent call site too (the option's type + default, and the one caller that passes it) so the claim covers the whole path rather than one hunk.
- **Attribute lint/prettier before reacting.** Lint the unpatched clone's copy first: pre-existing warnings (`exhaustive-deps` on `stashAt`, `no-restricted-globals` for `document` in test files) are not yours, and a whole-file formatter run ships unrelated churn. Prettier on a NEW file usually flags only the block you inserted — fix that hunk by hand.
- **Never park the scratch clone under the profile scratch dir** — that dir auto-prunes entries idle >24 h, and the prune is a recursive delete that FOLLOWS the `node_modules` junctions. A clone left there came back with its whole working tree gone (only `.git/objects` remained) and the live install's `node_modules` was one prune away from being wiped with it. Clone into a sibling of scratch (`<localappdata>/hermes/cache/upstream-pr-<pr>/clone`) and confirm both junctions exist before any test run.
- **A review that says a raised budget inverted an invariant: derive the guard, don't pick a new literal.** Raising a dial budget past the lease/timeout that keeps the dial's target alive inverts an invariant the old numbers happened to satisfy (30 s lease > 20 s dial became 30 s < 135 s, so the pruner could reap the switch target mid-dial and the dial then resolved on a closed socket). Fix the constant by DERIVING it from the budget in the same module (`ACTIVATION_LEASE_MS = SOURCE_SWITCH_DIAL_TIMEOUT_MS + margin`), grep the constant's other call sites, and expect a test that aged a fixture just past the old literal — it pins the old duration and has to move to the budget-derived age.
- **`git checkout` is blocked when the SESSION cwd is the managed checkout**, even if the command itself `cd`s into the clone — the guard reads the command line + session cwd, not your `cd`.
